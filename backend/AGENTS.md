This file provides guidance to AI coding agents (Codex / Claude Code 等) when working with code in this repository.

## 后端工程规范

本目录存放生产环境 NestJS 后端代码。

后端代码负责落地业务规则、安全边界、数据完整性以及系统可靠性。

---

## 1. 分层职责

推荐调用流向：
**HTTP 请求 → 控制器 → 应用 / 服务层 → 领域逻辑 → 持久层**

## 2. 控制器（Controller）

控制器职责：

- HTTP 请求解析
- DTO 数据绑定
- 输入校验边界
- 身份认证 / 权限鉴权边界
- 响应结果封装映射

**禁止**在控制器内编写大量业务逻辑。

## 3. 服务层（Service）

服务层负责：

- 业务流程编排
- 领域业务规则
- 事务边界管控
- 外部依赖协调调用

切勿为了缩减服务层代码量，把业务逻辑迁移到控制器。

## 4. 数据传输对象 DTO

DTO 用于定义数据传输边界。
⚠️ 不要默认认为：**DTO 等价于数据库实体模型**
二者职责完全不同。
业务逻辑执行前，必须完成外部入参校验。

## 5. 身份认证与权限鉴权

- **认证（Authentication）**：确认用户身份
- **鉴权（Authorization）**：校验操作权限

访问受保护资源时必须校验：

1. 用户是否已认证
2. 角色 / 操作权限
3. 资源归属权
4. 租户隔离边界
5. 业务操作专属鉴权逻辑

**绝不可以依赖前端做权限控制。**

## 6. 业务不变约束（Business Invariants）

业务强制约束必须在后端强制保障。
示例：

- 订单结算完成后不可取消
- 库存不允许出现负数
- 用户不能修改其他租户的数据
- 唯一性业务操作不可重复执行

不能依靠前端页面状态来保证业务约束。

## 7. 并发处理

每一个数据变更接口都要思考：

> 
> 如果两个请求同时执行，会发生什么？

可选方案：

- 数据库唯一约束
- 数据库事务
- 原子更新语句
- 乐观并发控制
- 悲观锁
- Redis 分布式锁
- 幂等设计

## 8. 幂等性

凡是可能被重试调用的操作，都需要评估幂等能力。
场景示例：

- 创建订单
- 支付处理
- Webhook 回调
- 异步任务执行
- 调用第三方外部接口

重试请求**不能产生重复的业务副作用**。

## 9. 错误处理

使用语义清晰的错误分类。
**禁止向客户端暴露以下信息：**

- SQL 原始报错
- 程序堆栈信息
- 底层基础设施细节
- 密钥、敏感凭证
- 内部实现细节

## 10. 外部依赖服务

对接第三方服务时，必须定义：

- 请求超时时间
- 重试策略
- 重试次数上限
- 服务降级失败处理逻辑
- 日志埋点
- 可观测监控

不要假设外部服务永远可以正常返回结果。

## 11. 数据库事务

当一次业务需要多次写入、并且要保证业务约束时，使用事务。
不要滥用事务。
需要考量：

- 锁持有时长
- 事务隔离级别
- 锁竞争冲突
- 外部调用带来的副作用

**禁止：在数据库事务开启期间，长时间等待外部第三方服务响应。**

## 12. 可观测性

生产关键业务操作，日志信息需要足够用于排查问题：

- 请求上下文
- 用户 / 租户上下文（适用场景下）
- 当前执行操作
- 失败原因
- 接口耗时延迟
- 第三方依赖故障

严禁打印密钥以及各类敏感数据。

## 13. 后端开发「完成定义」DoD

功能提测交付前必须完成检查：

- ✅ 业务规则全部后端落地
- ✅ 权限鉴权逻辑复核完成
- ✅ 并发场景评估复核
- ✅ 幂等性评估复核
- ✅ 异常分支路径完整复核
- ✅ 数据库影响评估
- ✅ Redis 使用影响评估
- ✅ 相关测试用例全部通过
- ✅ TS 类型检查通过
- ✅ 代码 Lint 校验通过

### 术语小注解

1. **Business Invariants**：业务不变约束，业务上永远不能被打破的硬性规则
2. **Idempotency**：幂等，多次执行得到和一次执行一样的业务结果，不会重复生成数据
3. **Tenant**：租户，多租户系统里的业务隔离单元
4. **DoD Definition of Done**：交付完成标准，团队约定什么才算功能真正开发完毕
5. **Observability**：可观测性，日志、监控、链路追踪，方便线上排查问题
