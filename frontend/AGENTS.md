# 前端工程规范

## 1. 适用范围

本规范适用于前端应用。

技术栈：

- React
- TypeScript
- TanStack React Query
- Zustand
- 生产环境浏览器运行时

## 2. 状态架构

前端分为三大核心状态分类：

- UI 状态 → React
- 客户端状态 → Zustand
- 服务端状态 → TanStack React Query

禁止用同一种状态方案包揽所有场景。

## 3. React 本地状态

以下场景优先使用 React 本地状态：

- 弹窗显隐
- 激活标签页
- 临时输入内容
- hover 悬浮状态
- 局部交互状态

若无充分理由，不要将本地状态提升到 Zustand。

## 4. Zustand

Zustand 负责管理客户端状态。

适用场景示例：

- 仅客户端生效的业务流程
- 本地偏好设置
- 跨组件业务流程
- 临时编辑状态

每个 Store 必须明确：

- 归属职责
- 生命周期
- 初始化逻辑
- 状态修改权责
- 重置行为
- 持久化行为

避免构建庞大的全局大 Store。

## 5. TanStack React Query

TanStack React Query 负责管理服务端状态。

示例：

- 用户数据
- 订单
- 商品
- 权限
- 通知
- 远程配置

把 React Query 当作**服务端状态生命周期管理器**，而不只是简单的请求封装工具。

## 6. React Query 与 Zustand 的边界

✅ 推荐数据流：
后端数据 → TanStack React Query → 组件

❌ 避免数据流：
后端数据 → React Query → useEffect → Zustand → 组件

不要仅仅因为多个组件需要这份数据，就把服务端数据复制一份存到 Zustand。

如果确实需要数据复制，必须文档记录：

- 唯一数据源
- 数据同步方向
- 同步触发条件
- 缓存失效策略
- 过期数据处理逻辑

## 7. Query Key（查询键）

Query Key 必须完整表达服务端数据的唯一标识。

当接口返回结果依赖以下因素时，Query Key 必须包含全部依赖项：

- 资源 ID
- 租户
- 当前用户
- 筛选条件
- 排序规则
- 分页参数

禁止使用信息不完整的 Query Key。

## 8. Query Key 设计规范

整个项目保持统一的 Query Key 书写约定。
项目复杂度较高时，建议使用 Query‑Key 工厂函数。

不要随意混用多种写法，例如：
`['orders']`、`['order', id]`、`['orders:list']`、`['orders', 'detail', id]`，
每种写法都要有明确架构考量，不能随意乱写。

## 9. 查询函数（Query Functions）

查询函数应当做到：

- 调用接口层
- 保留完整类型
- 统一异常处理
- 和 UI 逻辑解耦

不要在查询函数内部写大量业务逻辑。

## 10. 数据过期时间 staleTime

不要无脑直接写：
`staleTime: 0` 或者 `staleTime: Infinity`

基于业务语义判断数据可容忍的过期时长。
思考问题：这份数据允许多久不更新？

## 11. 缓存失效

执行修改操作（mutation）后，明确哪些查询会受影响。
优先使用精准定向失效。
禁止默认直接清空全部缓存。

## 12. 直接更新缓存

满足以下条件时，使用缓存直接更新：

- 服务端返回结果是权威数据源
- 清楚会影响哪些缓存条目
- 充分理解数据一致性带来的影响

优先选择缓存失效的场景：

- 会影响多条资源
- 业务规则复杂
- 数据正确性优先级高于避免重复请求

## 13. Mutation 修改请求

每一个关键的修改请求，都需要考虑：

- 重复提交
- 重试策略
- 幂等性
- 乐观更新
- 回滚逻辑
- 缓存失效
- 过期状态
- 并发修改
- 鉴权失败

## 14. 乐观更新 Optimistic Updates

仅在以下条件全部满足时使用乐观更新：

- 操作结果可预判
- 请求失败可以恢复
- 回滚逻辑可靠
- 清楚并发带来的行为问题

不要单纯为了视觉上感觉更快就使用乐观更新。

## 15. 竞态条件

永远不要假设请求顺序和响应返回顺序一致。

> 
> 示例：请求 A → 请求 B → B 先返回 → A 后返回

需要审查关注点：

- Query Key
- 请求参数
- Mutation 执行顺序
- 缓存失效逻辑
- 请求取消
- 过期响应数据

## 16. 请求取消

针对频繁变化的请求场景：

- 搜索联想
- 搜索输入
- 筛选切换

考虑做请求取消处理。
但请求取消并不能解决全部过期响应问题。

## 17. 加载状态

区分不同加载类型：

- 首次初始化加载
- 获取数据中 fetching
- 重新拉取 refetching
- Mutation 执行中
- 后台静默刷新

后台刷新时，不要直接用全屏 loading spinner 覆盖已有可用旧数据。

## 18. 错误状态

区分各类错误场景：

- 首次请求失败
- 后台刷新失败
- 修改请求失败
- 登录鉴权失效
- 权限不足
- 网络错误
- 超时
- 业务逻辑错误

不要把所有错误统一展示成同一种 UI。

## 19. 派生状态

不要存储可以通过计算得到的值。
✅ 推荐：原始状态 → 计算派生得到新值
❌ 避免：复制一份冗余存储状态

## 20. Effects 副作用

写 useEffect 之前先自问：
这个副作用是用来和哪个外部系统做同步？

不要用副作用做这些事：

- 做值的派生计算
- 普通计算逻辑
- 事件处理
- 不必要的数据同步

## 21. 记忆缓存

不要无脑滥用：
`useMemo`、`useCallback`、`React.memo`

只有确实存在可感知性能问题时才使用。

## 22. 类型安全

尽量避免：
`any`、`as any`、`@ts‑ignore`

不要为了绕过编译报错削弱类型安全。

优先使用：

- 显式声明类型
- 泛型
- 类型守卫
- 可区分联合类型
- 接口边界处做运行时校验

## 23. 浏览器运行时环境

代码需要兼容这些浏览器现实场景：

- 页面刷新
- 多标签页
- 弱网
- 离线状态
- 登录凭证过期
- 用户重复点击交互
- 浏览器前进后退
- 请求被中断
- 页面可见性切换

不要假设浏览器生命周期永远完美运行。

## 24. 前端交付完成标准 Definition of Done

交付前审查清单：

- 状态归属职责
- Query Key 设计
- 缓存行为
- staleTime 过期时间
- 缓存失效逻辑
- Mutation 修改行为
- 竞态条件
- 各类加载状态
- 各类错误状态
- 浏览器异常生命周期
- 类型安全
- 无障碍访问（如适用）
- 性能影响评估
- 生产环境构建验证
