## 诊断：Windows 开发控制台中文乱码（宸茶繛鎺）

- 现象：日志中文变 `宸茶繛鎺?` / `杩炴帴姝ｅ父`，但 `console.log('中文')` 正常。
- 根因（非应用 bug）：transport worker 线程用 `StringDecoder('utf8')` 还原字符串后交给 sonic-boom（`pino-pretty` / `pino/file`），sonic-boom 以 **UTF-8 裸字节写 fd 1**，绕过 `WriteConsoleW`；Windows 控制台默认代码页 936(GBK) 把 UTF-8 字节按 GBK 解码 → 乱码。主线程 console.log 走 uv_tty→WriteConsoleW 所以正常。
- 证据：`已连接` 的 UTF-8 字节 E5B7B2 E8BF9E E68EA5 按 GBK 解码恰为 `宸茶繛鎺?`（末字节落单 → `?`）。
- 结论：终端编码问题，文件落盘（UTF-8）与 Linux 生产不受影响，应用侧不改。
- 处理：`src/shared/logger/README.md` 故障排查新增该条目，给出 `chcp 65001` 与系统「Beta: 使用 Unicode UTF-8」两种解法，并明确不要为迁就控制台改日志编码（pino 无编码开关，会连生产一起弄坏）。
- 未采纳方案：dev 环境改用主线程内联 pino-pretty（需 `[opts, stream]` 元组、放弃 worker 且无法与 `transport.targets` 多路输出共存）；应用内自动 `chcp`（会污染用户终端且 Linux 下是死代码）。

## 修复：请求到达日志被误记为 WARN（`HTTP POST /api/auth/login received`）

- 现象：每条访问日志的 received 行都打成 `WARN`。
- 根因：pino-http 11 的 `customLogLevel(req, res, err)` 会被调用**两次**——① 请求到达时（`err=undefined`，源码 `getLogLevelFromCustomLogLevel(customLogLevel, useLevel, res, undefined, req)`），② 响应结束时。原实现末段为 `if (!res.writableEnded) return 'warn'`，而请求到达时抛出的 `res.statusCode` 继承原型默认 `200`、`res.writableEnded` 恒为 `false`（`OutgoingMessage` getter 返回 `this.finished`，`end()` 前为 false）→ 命中 warn。该分支本意只想覆盖「客户端中断」，却被 received 时点共享。
- 修复（`src/shared/logger/logger.module.ts`）：`if (res.headersSent && !res.writableEnded) return 'warn';`。received 时 `headersSent=false` → info；正常结束 `writableEnded=true` → info；已开始写响应却未结束（中断/超时）→ warn。已知边界：响应头尚未发出即被中断的请求会按 info 记（信息量极低，可接受）。
- 校验：IDE lint 无报错；shell 仍不可用（spawn bash ENOENT），tsc/lint/build 未实际运行。

## 决策（方案 A）：移除「请求到达」访问日志，customLogLevel 回归三行

- 背景：上一条 WARN 修复是「打补丁区分两个时点」。进一步评估后判定 received 行在企业级不该常态存在，用户拍板方案 A。
- 结论与理由：访问日志只保留响应结束的一条。① 日志量对半砍（访问日志是最高频日志，按 GB 计费）；② 到达行无 statusCode/responseTime/业务字段，纯噪声且会污染基于 level 的告警；③ start/end 配对是 APM/OpenTelemetry 职责，access log 只该记结果；④ 重试风暴下噪声被放大。项目当前无 OTel，排障可临时 `LOG_LEVEL=debug` 用应用日志兜底。
- 变更：
  - `src/shared/logger/logger.module.ts`：删除 `customReceivedMessage`；`customLogLevel` 由 `if (res.headersSent && !res.writableEnded) return 'warn'` 回归为 `if (!res.writableEnded) return 'warn'`（无到达日志后该函数只在响应结束时被调用，语义恢复无歧义），并加注释警示「若重新引入到达日志必须重新区分两个时点，否则到达日志会被判 warn」。
  - `src/shared/logger/README.md`：新增「每个请求只产出一条访问日志（无『请求到达』日志）」小节，含原因与重启风险警示。
- 影响：`requestId` 关联、健康探针过滤、慢请求 `[SLOW]` 标记、中断告警均不受影响；全仓库无测试/文档引用 `received`。
- 未跟进（用户未拍板）：`.env` 与 `configuration.interface.ts` 称慢请求记 warn，实现只加 `[SLOW]` 且级别仍 info，三处口径不一致。

## 修复：字段契约收敛 + 消除 4xx 双写（上一轮评审的第 1 项）

## 核实：req 序列化器要不要加 headers（只核实/评审，未改代码）

- 用户问「是不是少了 headers」「企业级要不要加 `headers: req.headers`」。
- 核实结论 A（纠正旧注释）：`pino-std-serializers@7.1.0` 的 `index.js` 中 `wrapRequestSerializer` 实现为
  `custom(reqSerializers.reqSerializer(req))`；`lib/req.js` 的 `reqSerializer` 返回对象**含自有可枚举的 `headers`**
  （值即 `req.headers`），另有 id/method/url/query/params/remoteAddress/remotePort。
  → `logger.module.ts:199-201` 注释「只保证 method/url、不要依赖 headers」**不准确**，运行时 `req.headers` 存在。
- 核实结论 B（**重要安全缺陷**）：`redact.paths` 中 `req.headers.authorization` / `req.headers.cookie` /
  `res.headers["set-cookie"]` **恒为死路径**，证据链：
  ① pino-http@11.0.0 `logger.js`：`reqKey = customAttributeKeys.req`（项目配 `'request'`），
     请求对象经 `log.child({ [reqKey]: req })` 绑定，序列化器也注册在 `serializers[reqKey]` → 顶层键是 `request`；
  ② pino@10.3.1 `lib/tools.js` 的 `asChindings`：先 `serializers[key](value)`，再
     `(stringifiers[key] || wildcardStringifier || stringify)(value)` —— 脱敏 stringifier **按顶层键名索引**；
  ③ 因此路径必须写成 `request.headers.*` / `response.headers[...]` 才可能生效。
  当前不泄露的唯一原因是自定义 req 序列化器只返回 `{ method, url }`、未输出 headers；
  `README.md:155-156`「redact 已内置 authorization/cookie/set-cookie」是虚假安全感。
- 评审建议（未实施）：不要加整包 `headers: req.headers`（凭证泄露 / KB 级体积 / UA·referer 高基数 /
  客户端可控的注入面 / 与 ADR-002 单一字段路径契约冲突）。若要加则加白名单
  （`user-agent` / `content-type` / `referer`（必须过 `sanitizeUrl`）），并同步修正或删除那 3 条死脱敏路径；
  `clientIp` 需先定 trust proxy 层数（`main.ts` 当前为注释状态）。
- 已给用户两个选项：A 只修脱敏路径（最小安全改动）；B 白名单 + 修脱敏 + 更新 ADR/README。等待拍板。
- 工具经验：本仓库未安装 node_modules，无法读本地依赖源码；改用 `web_fetch` 抓 unpkg 上锁定的版本
  （`pino@10.3.1` / `pino-http@11.0.0` / `pino-std-serializers@7.1.0`），可直接读到逐字源码。
  注意 `pino-http` 入口是 `logger.js`（不是 `index.js`），`pino-std-serializers` 入口是根 `index.js`（不是 `lib/index.js`）。
  另：pino 10 的脱敏库是 `@pinojs/redact@0.4.0`（**不是 fast-redact**，`pnpm-lock.yaml` 里搜 `redact` 只有 `@pinojs/redact`）。

## 答疑：SSE 访问日志为什么没有 requestId（只分析，未改代码）

- 用户贴两条日志对比：`GET /api/jobs/2174…/events` 200 / 2628ms / `[SLOW]` 且**无** `requestId`、无 `bizCode`；`GET /api/user/list` 404 有 `requestId` + `bizCode`。问「有一个没有 requestId 是否正常」。
- 结论：**不正常**，是可解释的确定性缺陷，不是偶发。顶层 requestId/bizCode 的唯一来源是 pino `mixin` 读 ALS（`logger.module.ts:254-262`）；第二条日志有 requestId 即证明 mixin 与 `LOG_INCLUDE_CONTEXT` 正常，问题只出在「这次请求的 ALS 上下文取不到」。
- 机制（证据链）：
  - store 只在 `requestContextStorage.run({}, () => next())`（`request-context.middleware.ts:9-12`）派生的异步链里存在；`setRequestId` 也只写这个 store（`request-context.ts:50-55`）。
  - SSE 走 `@Res()` 手动收尾：`res.end()` 在 `cleanup()` 内（`jobs.controller.ts:137-146`），触发源是 `req.on('close', cleanup)`（`:162`）或 `jobEvents.subscribe()` 回调（`:154`）；事件来自 Redis Pub/Sub 的 subscriber 回调（`job-events.service.ts:106-115`）或 worker 里的 `publish`（`job-record.service.ts:375-392`）——都不属于本请求的 ALS 链。
  - 上述回调运行在 **root 上下文**（socket close / redis 客户端 socket 回调都是进程启动时注册的），因此 `res` 的 `finish`/`close` 在 root 上下文 emit → mixin 读到 `{}` → 该条日志缺 `requestId`/`bizCode`。
  - 唯一带得上 requestId 的 SSE 路径是「连接时任务已是终态」，`cleanup()` 由 controller 同步调用（`:172-174`）→ 表现为「有时有、有时没有」。
- 附带核实（`web_fetch` 读 pino-http@11.0.0 `logger.js` 源码）：访问日志由 `onResponseComplete` 产出，注册在 `res.on('close')` + `res.on('finish')`（首次触发即摘除三个监听器）；`wrapChild` 只把 opts 透传给 pino，**mixin 由 pino 求值**，与 ALS 强耦合。顶层 `reqId` 绑定**只在 `quietReqLogger: true`** 时才建（`logger.child({ [customAttributeKeys.reqId]: req.id })`），默认 false 时 reqId 只以 `req.id` 藏在 `request` 序列化对象里。
- 影响：① SSE 访问日志无法与该请求的应用日志、以及 `RequestIdMiddleware` 已回写的 `x-request-id` 响应头关联；② 每个持续 > `LOG_SLOW_REQUEST_THRESHOLD`(500ms) 的 SSE 连接都被无条件标 `[SLOW]`（`responseTime` 对 SSE 是连接时长而非处理耗时）→ 持续给慢请求告警制造噪音。
- 建议修复（未实施，等拍板）：
  - A（推荐）：让**访问日志**的 requestId 脱离 ALS，改用 pino-http 的 per-request 绑定 —— `quietReqLogger: true` + `customAttributeKeys.reqId: 'requestId'`（源码已确认这是唯一能产生顶层 reqId 绑定的开关）；或 `customProps: (req) => ({ requestId: req.id })`（在 `onResFinished` 现场能拿到 req，但该选项官方标记 deprecated）。
  - B（最小局部）：SSE controller 捕获 store，`cleanup()` 内 `requestContextStorage.run(store, () => res.end())`；只修这一处，不动日志管线。
  - 两者都需同步 `ADR-002` + `src/shared/logger/README.md`；另需单独决定是否把 SSE 排除出 `[SLOW]` 标记。
- 未执行校验：shell 不可用（spawn bash ENOENT），未运行 tsc/lint/test；结论来自代码阅读 + Node ALS 语义 + pino-http 源码核实。
