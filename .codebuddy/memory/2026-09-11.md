## 修复 logger.module.ts 类型编译错误（TS2339）

- 现象：`src/shared/logger/logger.module.ts` 中 `targets.push(...)` 报 TS2339，`targets` 被推断为 `readonly (... )[]`。
- 根因：pino/nestjs-pino 中 `transport.targets` 类型声明为 readonly 数组，`PinoTransportTargets = Extract<...>['targets']` 继承了 readonly，无法调用 `push`。
- 修复：先取元素类型，再重声明为可变数组：
  - `type PinoTransportTarget = Extract<NonNullable<PinoHttpOptions['transport']>, { targets: unknown }>['targets'][number];`
  - `type PinoTransportTargets = PinoTransportTarget[];`
- 仅类型层改动，运行时行为不变（写入 `{ transporter: { targets } }` 不受影响）。

## 修复启动崩溃：option.transport.targets do not allow custom level formatters

- 现象：启动即崩，`pino/lib/tools.js:342` 抛 `option.transport.targets do not allow custom level formatters`（链路 pino-http `wrapChild` → `pino()`）。
- 根因：`src/shared/logger/logger.module.ts` 同时使用了 `transport.targets`（多路输出）和 `formatters.level` 函数；pino 的 `normalizeArgs` 对二者组合是硬性禁止（`opts.transport.targets.length && typeof opts.formatters.level === 'function'` 即抛）。注意：该限制只针对 `targets` 数组形态。
- 方案评估：
  - 保留大写级别 → 只有两条路：① 不用 targets（无法覆盖 console+全量文件+error 文件三路）；② 自行 `pino.transport({targets})` 生成流后以 `[opts, stream]` 元组传给 nestjs-pino（nestjs-pino `rootLogger.js` 支持 `pinoHttp(...params)`，可行）——改动面与 worker 生命周期风险都不小。
  - 本次选最小改动：移除 `formatters.level`，level 回落为 pino 默认数字级别（30/40/50）。
- 变更：`logger.module.ts` 删除 `formatters.level` 并补注释；`src/shared/logger/README.md` 故障排查新增该报错条目，说明 level 为数字、开发控制台仍由 pino-pretty 显示 INFO/ERROR。
- 影响：JSON 日志（生产 stdout / app.log）`level` 由 `"INFO"` 变 `30`。此前该组合本就启动即崩、不存在可用行为，故不算破坏性回归；无测试依赖 level 文案（仅 `app.controller.spec.ts`）。
- 未执行校验：shell 仍不可用（spawn bash ENOENT），tsc/lint/build 未实际运行；IDE lint 对该文件无报错。

## 诊断：Windows 开发控制台中文乱码（宸茶繛鎺）

- 现象：日志中文变 `宸茶繛鎺?` / `杩炴帴姝ｅ父`，但 `console.log('中文')` 正常。
- 根因（非应用 bug）：transport worker 线程用 `StringDecoder('utf8')` 还原字符串后交给 sonic-boom（`pino-pretty` / `pino/file`），sonic-boom 以 **UTF-8 裸字节写 fd 1**，绕过 `WriteConsoleW`；Windows 控制台默认代码页 936(GBK) 把 UTF-8 字节按 GBK 解码 → 乱码。主线程 console.log 走 uv_tty→WriteConsoleW 所以正常。
- 证据：`已连接` 的 UTF-8 字节 E5B7B2 E8BF9E E68EA5 按 GBK 解码恰为 `宸茶繛鎺?`（末字节落单 → `?`）。
- 结论：终端编码问题，文件落盘（UTF-8）与 Linux 生产不受影响，应用侧不改。
- 处理：`src/shared/logger/README.md` 故障排查新增该条目，给出 `chcp 65001` 与系统「Beta: 使用 Unicode UTF-8」两种解法，并明确不要为迁就控制台改日志编码（pino 无编码开关，会连生产一起弄坏）。
- 未采纳方案：dev 环境改用主线程内联 pino-pretty（需 `[opts, stream]` 元组、放弃 worker 且无法与 `transport.targets` 多路输出共存）；应用内自动 `chcp`（会污染用户终端且 Linux 下是死代码）。
