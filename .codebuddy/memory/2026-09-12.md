## 排查 POST /api/background-tasks/export-report 500（BullMQ Custom Id cannot be integers）

- 现象：提交任务时 500（bizCode B0001），日志 `context: JobService` 记录 `Failed to enqueue jobId=217432768118784000 name=export-report`，
  `err.message = Custom Id cannot be integers`，栈指向 `bullmq/dist/cjs/classes/job.js:906 Job.validateOptions`。
- 根因（已核实源码，非推断）：BullMQ 禁止 **custom jobId 为纯整数字符串**。
  `job.js:904-907` 的校验是 ``if (`${parseInt(this.opts.jobId, 10)}` === this.opts.jobId) throw new Error('Custom Id cannot be integers')``，
  **字符串形态才会命中**（number/bigint 因 `===` 类型不同反而不命中）。
- 项目侧证据链：
  - `src/shared/utils/snowflake.ts` `generateSnowflakeId()` 返回**纯数字字符串**。
  - `job-record.service.ts` `createQueued` → `toDomain` 返回 `id: row.id.toString()`，故 `run.id` 是纯数字字符串。
  - `job.service.ts:70-82` 把 `run.id` 同时塞进 `data.jobId` 与 `opts.jobId`。
- **间歇性成因（可推导，未实测）**：雪花 ID ≈ 2.17e17 > 2^53，`parseInt` 会先转 double（该量级 ULP = 2^5 = 32），
  仅当 ID 本身是 32 的倍数（即低 12 位 sequence ≡ 0 mod 32）时 `parseInt` 结果 toString 才与原串一致 → 约 **1/32 概率抛错**，
  其余情况因精度舍入而侥幸通过。报错的 217432768118784000 恰为 32 的倍数，与该推断吻合。
- **第二处同类缺陷**：`job.service.ts:207-210`（`compensate` 重新入队）也用 `run.id.toString()` 作 `opts.jobId` → 死信补偿的重入队路径同样必然失败。
- 修复方向：仅给 **BullMQ 的 `opts.jobId`** 加非数字前缀（推荐 `job-${id}`，不得用 `:`，BullMQ 限制 `split(':').length === 3`）；
  **`data.jobId` 必须保持纯雪花 ID**（`job.processor.ts` 用 `BigInt(jobId)` 反查 DB）。
  建议收敛在 `JobQueueService.enqueue` 内部统一加前缀，避免调用方遗漏。
- 存量兼容：`job_runs.bullJobId` 存的是 BullMQ 实际 id，旧记录仍可 `getJob`/`remove`；新记录带前缀，DB `job_runs.id` 仍是唯一权威标识。
- 附带观察（非本次问题）：日志 JSON 中顶层 `requestId` 出现两次 —— pino-http 请求级 child binding 与 `mixin` 同键，
  pino 以字符串拼接输出导致重复键（值相同，后者覆盖），无正确性影响。
- 未执行校验：本机 `execute_command` 不可用（spawn bash ENOENT，2026-09-12 再次实测确认），未运行 tsc/lint/测试。

## 修复：BullMQ jobId 加非数字前缀（已实施）

- 改动文件：
  - `src/shared/jobs/queue/job-queue.service.ts`：新增模块级 `BULL_JOB_ID_PREFIX = 'job-'` 与幂等转换 `toBullJobId()`

- 设计要点：转换收敛在 queue 层唯一入口，故 `JobService.submit`（第 70 行）与 `compensate`（第 207 行）两个调用点
  **无需改动即同时修复**；`data.jobId` 保持纯雪花 ID（worker `BigInt(data.jobId)` 反查 DB 不能被污染）；
  前缀用 `-` 而非 `:`，同时避开 BullMQ 两条校验。`options.jobId` 注释已更正为「业务雪花 ID」，不再误导为「默认使用 data.jobId」。
- 兼容性：`job_runs.bull_job_id` 存的是 BullMQ 实际 id，旧记录（无前缀）仍可 getJob/remove；
  权威标识仍是 `job_runs.id`，幂等语义不变（前缀转换确定性）。存量因本 bug 失败的记录已被标 failed 终态，无需数据修复。
