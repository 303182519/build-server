## Jobs SSE 端点静态评审（`src/shared/jobs/jobs.controller.ts` `getEvents` 82-175 行）

仅评审，未改代码；本工作区 `execute_command` 不可用，未运行 `tsc` / `eslint` / 测试。

结论：3 处 P0 + 3 处 P1 + 若干 P2，均已定位到行号。

### P0（必须修）
1. **写失败路径不回收资源 → 计数器只增不减**：`safeWrite` catch 只置 `closed=true`（122-135），而 `cleanup()` 首行 `if (closed) return`（138）→ `activeSseConnections` 永不递减（泄漏 100 次后该实例所有 SSE 恒 503，需重启）、`setInterval` 与 RxJS 订阅泄漏；170 行 `return` 时响应头已 flush 但未 `res.end()` → 连接悬挂。根因：`closed` 同时表示「已关闭」与「写失败」，置位与清理被拆成两条路径。
2. **上限检查与占用间存在 `await`（超卖）**：检查在 90 行、`++` 在 117 行，中间隔 `await getById`（99）+ 鉴权 → 并发放行超出 `MAX_SSE_CONNECTIONS`。修复时须注意早退路径释放计数，否则退化为缺陷 1。
3. **`snapshot` 查询早于订阅建立 → 终态事件丢失**：查询在 99 行、订阅在 154 行（Subject 无回放、Redis Pub/Sub fire-and-forget，窗口内事件直接丢弃），而 172 行用旧 `snapshot.status` 判终态 → 不清理，客户端永久挂住。快任务（steps=1, delay=0）可稳定命中。

### P1
4. 背压分支是死代码（122-130 两个分支都 `return true`，慢客户端无上界缓冲）。
5. 503 响应手写 `code:'15503'` 绕过 `StandardResponse` 契约（缺 `bizCode`/`data`/`path`/`requestId`，且不执行 `setBizCode()` 丢失访问日志顶层 `bizCode` 维度）；该处未发 SSE 头，应改为 `ErrorException`。`'15503'` 符合 MMSNN（jobs 模块 15 + 5xx 段，已有 15501）。
6. owner 校验不一致：SSE 做了严格 `createdBy` 校验（103-109），但 `list` / `getById` / `cancel` / `compensate` 全无校验 → 越权读他人 payload/result、取消/补偿他人任务；另 SSE 对 `createdBy=null` 系统任务一律 403（管理员亦然）需确认是否预期。

### P2
- 缺 `res.on('error')`；`req.on('close')` 可换 `res.on('close')`。
- 缺 `X-Accel-Buffering: no`（Nginx 缓冲）；`Connection: keep-alive` 可移除。
- `cleanup` 引用其后声明的 `heartbeatInterval`/`subscription`（137/149/154），当前靠同步时序侥幸安全，插入 `await` 即成 `ReferenceError`。
- `static` 计数器为进程内（多实例真实上限 = 100×实例数），且未按用户限制。
- 未处理 `Last-Event-ID`；`id:'snapshot'` 与递增序号属不同 id 空间；若改原生 EventSource，服务端 `end()` 会触发自动重连风暴。
- `src/shared/jobs` 下无 `*.spec.ts`。

### 客户端事实
- `client/js/export-report-sse.js` 用 `fetch` + `ReadableStream` 手动解析 SSE（原生 EventSource 不能带 Authorization），并在终态事件后自行处理，不依赖重连。

修复要点：

3. 订阅提前到快照读取之前，快照下发前的事件先进入 `conn.pending` 缓冲、快照写完后再按序回放（消除终态事件丢失窗口）。
