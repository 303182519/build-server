# 后端工程规范

## 1. 适用范围

本规范适用于 NestJS 后端项目。

## 2. 架构

依赖流向优先遵循：
HTTP 请求 → 控制器 → 应用层 / 服务层 → 领域业务逻辑 → 持久化层
若现有仓库架构存在刻意差异化设计，则遵从原有架构。

## 3. 控制器

控制器主要职责：

- HTTP 请求入参接收
- DTO 数据绑定校验
- 认证上下文处理
- 权限校验边界拦截
- 接口响应数据封装映射

**禁止在控制器中编写大量业务逻辑**。

## 4. 服务层

服务层负责：

- 业务流程编排
- 业务规则实现
- 事务边界管控
- 对接协调外部依赖服务

## 5. 数据传输对象（DTO）

DTO 用于定义接口传输层的数据边界。
⚠️ 不要默认 DTO 和 Prisma 数据库模型完全等同。
执行业务逻辑前，必须对外部传入数据做校验。

## 6. 业务不变约束

业务强制校验规则**必须在服务端实现**。
示例场景：

- 资源归属权限校验
- 多租户数据隔离
- 合法状态流转校验
- 操作唯一性约束
- 库存数量限制

## 7. 身份认证

认证用于确认请求方身份。
**绝不可以认为完成身份认证就等同于拥有操作权限**。

## 8. 权限鉴权

权限校验必须在后端强制执行。
校验维度参考：

- 角色
- 权限点
- 资源归属关系
- 租户数据边界
- 业务操作专属权限

前端权限判断仅作用户体验优化，不能作为安全依据。

## 9. 并发处理

会修改数据状态的操作，必须考虑并发执行场景。
处理手段参考：

- 数据库事务
- 数据库原子操作
- 数据库唯一约束
- 乐观并发控制
- 锁机制
- 幂等性设计

## 10. 幂等性

存在重试可能性的操作，必须明确设计幂等语义。
重点场景：

- 资源创建类接口
- 支付相关操作
- Webhook 回调
- 后台任务
- 第三方外部系统对接

## 11. 异常处理

禁止对外暴露以下信息：

- SQL 原始报错
- 程序堆栈信息
- 密钥、敏感凭证
- 内部基础设施细节

使用业务层统一、稳定的错误码 / 错误语义对外返回。

## 12. 外部服务调用

对接每一个外部依赖服务，都需要考虑：

- 请求超时时间
- 重试机制
- 重试次数上限
- 服务失败降级行为
- 可观测性（日志 / 监控）
- 幂等性保障

永远不要假设外部服务永远可用。

## 13. 数据库事务

当多个数据库操作需要保证业务约束一致性时，使用事务。
需要权衡：

- 事务执行时长
- 锁持有时间
- 事务隔离级别
- 锁竞争风险
- 事务内产生的外部副作用

不要无意义地长时间持有事务。

## 14. 查询性能

代码评审需要关注：

- N+1 查询问题
- 返回结果无上限的查询
- 缺失必要索引
- 返回数据集过大
- 多余联表 Join
- 分页逻辑
- 排序逻辑

## 15. 日志打印

日志需要便于问题排查，记录内容包含：

- 执行的业务操作
- 请求相关上下文
- 用户 / 租户上下文（适用场景下）
- 耗时延迟
- 依赖服务异常
- 失败根本原因

严禁打印密钥、凭证等敏感信息到日志。

## 16. 后端完成定义（DoD，完成准入检查项）

提交前需要评审核对：

- DTO 参数校验
- 接口权限鉴权
- 业务不变约束校验
- 并发安全处理
- 幂等性设计
- 事务边界是否合理
- 异常错误处理
- 数据库性能影响
- Redis 使用影响
- 外部依赖异常行为处理
- 项目构建打包

> 
> 术语备注
> 
> 
> - DTO：Data Transfer Object 数据传输对象
> - Prisma：NodeJS ORM 数据库框架
> - DoD：Definition of Done，研发 “完成” 的验收标准
> - Idempotency：幂等性，多次执行效果和一次执行一致
> - Business Invariants：业务不变约束，业务必须永远成立的规则
